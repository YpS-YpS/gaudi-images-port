tl;dr — one command on a fresh box

git clone https://github.com/YpS-YpS/gaudi-images-port.git
cd gaudi-images-port
sudo ./bootstrap.sh --with-gemma4          # ~30-60 min; reboots once if kernel swap is needed

That installs kernel 6.8, the Habana driver, hugepages, NICs, Docker; pulls the two vLLM base images; builds the patched Gemma 4 image; downloads both models; launches Qwen 32B-Thinking on port 8000 and Gemma 4 on port 8004.

After bootstrap, every other model is one line: vllm-launch <preset> — see the table below.

Launchpad — interactive picker

If you'd rather not memorize preset names, run the interactive launchpad (also in bin/):

./bin/launchpad

It shows the current card matrix (per-card HBM bars, which container owns each), a numbered menu of every preset, prompts for card overrides (e.g. run minimax-m2 on Gaudis 0-3 instead of 4-7), waits for the endpoint to be ready, fires a 17×89 smoke test, and prints a launch report. 📐 Scaling math — why MiniMax can't run at TP=6

When I tried to scale MiniMax to 6 Gaudis (after freeing the Qwen cards), the answer was no — but not because of HBM. It's a hard mathematical constraint baked into the model architecture. This is worth documenting because the same logic applies to any tensor-parallel sharding decision on this box.

The rule

vLLM (both upstream and the HPU path) requires every per-layer parallelizable dimension to be evenly divisible by the tensor-parallel size TP. For an MoE model like MiniMax, that means three constraints, all of which must hold simultaneously:

# Constraint 1 — attention sharding
num_attention_heads  mod  TP  ==  0

# Constraint 2 — KV cache sharding (the binding one for MiniMax)
num_key_value_heads  mod  TP  ==  0

# Constraint 3 — expert sharding
num_local_experts    mod  TP  ==  0

If any one fails, vLLM refuses to load the model — it can't split the weights cleanly across cards.

The numbers (read straight from config.json)

FieldMiniMax M2MiniMax M2.7Divisors ≤ 8
num_attention_heads4848{1, 2, 3, 4, 6, 8}
num_key_value_heads88{1, 2, 4, 8} ← binding
num_local_experts128256{1, 2, 4, 8}
hidden_size30723072{1, 2, 3, 4, 6, 8}

Taking the intersection of all three constraints — the set of TPs that divide every required dimension:

valid TP = divisors(48) ∩ divisors(8) ∩ divisors(128 or 256)
         = {1, 2, 3, 4, 6, 8} ∩ {1, 2, 4, 8} ∩ {1, 2, 4, 8, …}
         = {1, 2, 4, 8}
TP=6 fails because 8 KV heads ÷ 6 cards = 1.33. Each card would have to hold 1.33 KV heads, which is not a whole number — vLLM can't split that. The same applies to TP=3, 5, 7.

What that means for the 8-card box

On 8 Gaudi 3 cards, MiniMax can only be run at one of these scales:

TPCards usedWeights / card (M2.7, 230 GB)Notes
11~230 GBDoesn't fit (128 GiB HBM)
22~115 GBFits weights but no room for KV cache (~75 GB) + graph reserve (~21 GB) on a 128 GiB card
44~58 GB✓ The default. ~101 GB/card steady-state with tightened knobs.
66—Invalid — KV head split fails
88 (full box)~29 GB✓ Maximum throughput, but takes the whole box. Stops Gemma 4 on Gaudis 2/3 + anything on 0/1.

The other dimensions are slack

Note that num_attention_heads = 48 would have allowed TPs of 3, 6, 12, 16, 24, 48 — many more options. num_local_experts = 256 allows 16, 32, 64, 128, 256. So the binding constraint is always num_key_value_heads = 8 on MiniMax — that's what cuts the option set down to {1, 2, 4, 8}.

If MiniMax ever ships a variant with 16 or 32 KV heads, we could run TP=6 (among others) without issue. Until then, "scale up" on this model means TP=4 → TP=8, no intermediate stops.

How to check this for any model yourself

🔧 Patches & hacks applied to get things running

Vanilla Habana vllm-gaudi 0.19 ships without handlers for several upstream classes that newer model families depend on. The patches below are what closed those gaps.

Gemma 4 31B — five patches

Layered on top of Habana's vllm-0.19.0-ptfork base image. The Dockerfile that applies them is dockerfiles/Dockerfile.gemma4.

① bump transformers to 5.7

Gemma 4 needs the upstream Gemma4ForCausalLM class, which only landed in transformers ≥5.7. Habana's base image ships 4.55. Patch: explicit pip install transformers==5.7.0.dev + VLLM_SKIP_TRANSFORMERS_VERSION_CHECK=1 so vLLM doesn't refuse to start.

② head_size=512 added to the allow-list

Symptom: ValueError: head_size 512 not supported.

Why: Gemma 4 has heterogeneous attention — local layers use head_dim=256, global layers head_dim=512, alternating 5:1. vLLM's HPU attention backend only allow-lists 64, 80, 96, 112, 128, 192, 256.

Fix: add 512 to the supported head_size list in the HPU attention backend.

③ UniformTypeKVCacheSpecs unwrap

Symptom: Crash inside the KV cache allocator — it gets a UniformTypeKVCacheSpecs wrapper instead of an inner spec.

Why: vLLM 0.19 introduced this wrapper to support models with per-layer-varying head dimensions. vllm-gaudi 0.19 wasn't taught about it.

Fix: detect the wrapper class in the KV cache allocator and unwrap to spec.kv_cache_spec before computing sizes. Patch script: dockerfiles/patch_kv_divisibility.py.

④ tensor.size → int coercion (upstream float bug)

Symptom: TypeError: 'float' object cannot be interpreted as integer.

Why: An upstream vLLM site passes tensor.size (a Python float on this path) where an int is expected. Fixed in main but not in the 0.19 base.

Fix: int(...) coercion at the offending site.

⑤ skip_special_tokens default flip

Symptom: Gemma 4's <|channel|> / <|end|> markers get stripped from the output, so the reasoning parser sees nothing.

Why: vLLM defaults skip_special_tokens=True. Gemma 4's channel markers are special tokens.

Fix: flip the default to False for this model family in the OpenAI-compat layer.

MiniMax M2 / M2.7 — handcrafted HPU class

No patches needed. vllm-gaudi ships a complete handcrafted HpuMiniMaxM2ForCausalLM at /usr/local/lib/python3.12/dist-packages/vllm_gaudi/models/minimax_m2.py (504 lines). At import time it overrides vLLM's upstream MiniMaxM2ForCausalLM registration:

WARNING [registry.py:915] Model architecture MiniMaxM2ForCausalLM is already
registered, and will be overwritten by the new model class
vllm_gaudi.models.minimax_m2:HpuMiniMaxM2ForCausalLM.

That's the warning you'll see on launch — it's expected and means the HPU path is active. The class also handles M2.7's MTP (multi-token prediction) weights via get_spec_layer_idx_from_weight_name (lines 498-504), which maps them to layer indices num_hidden_layers + i.

gpt-oss — the bug we couldn't fix

The HPU MoE kernel torch.ops.hpu.mixture_of_experts.bias_fused_weights is binary (part of SynapseAI 1.24.0). It accepts swigluoai defaults (alpha=1.702, limit=7.0) — exactly gpt-oss's values — but produces incoherent logits for gpt-oss's specific MoE shape. We narrowed it down to either that kernel or the MXFP4 dequantizer in vllm_gaudi/models/gptoss_mxfp4.py. Either way, not patchable from user-space. Full trace + upstream-report draft in GPT-OSS.md.

🛠 Running fully manually (no vllm-launch script)

If you'd rather skip the launcher and run a raw docker run — for example to plug into another orchestrator — the exact env vars and flags for each preset live in bin/vllm-launch (see the PRESETS array around line 20 and the docker run block at line 114).

Generic template for any FP8 Qwen model on a single Gaudi:

docker run -d --runtime=habana --restart unless-stopped \
  --name vllm-myrun \
  -e HABANA_VISIBLE_DEVICES=0 \
  -e PT_HPU_LAZY_MODE=1 \
  -e PT_HPUGRAPH_DISABLE_TENSOR_CACHE=false \
  -e VLLM_GRAPH_RESERVED_MEM=0.3 \
  -e VLLM_SKIP_WARMUP=true \
  -e HF_HOME=/root/.cache/huggingface \
  --net=host --ipc=host --cap-add=sys_nice \
  -v $HOME/hf-cache:/root/.cache/huggingface \
  --entrypoint /bin/bash \
  vault.habana.ai/gaudi-docker/1.24.0/ubuntu24.04/habanalabs/vllm-0.17.1-ptfork-2.10.0:1.24.0-1007 \
  -lc 'exec vllm serve Qwen/Qwen3-VL-32B-Thinking-FP8 \
       --tensor-parallel-size 1 --host 0.0.0.0 --port 8000 \
       --enable-auto-tool-choice --tool-call-parser hermes \
       --reasoning-parser qwen3 \
       --max-model-len 16384 --gpu-memory-utilization 0.9 \
       --max-num-seqs 32 --trust-remote-code \
       --served-model-name qwen3-vl-32b-thinking'

For Gemma 4 / MiniMax: swap the image to gaudi-vllm-gemma4:0.19.0 (built via cd dockerfiles && docker build -t gaudi-vllm-gemma4:0.19.0 -f Dockerfile.gemma4 .), swap parsers to gemma4 or minimax_m2, set the right cards in HABANA_VISIBLE_DEVICES, and adjust --tensor-parallel-size to match.

🩺 Verifying the box

sudo bash scripts/check.sh                # readiness — green/red checklist
sudo bash scripts/verify.sh                # + hl_qual + API smoke
scripts/smoke.sh http://localhost:8004 gemma4-31b      # per-endpoint full smoke
scripts/quality-bench.sh                   # cross-endpoint domain-knowledge bench

The smoke.sh battery exercises /v1/models → plain text → vision (inline PNG) → single tool call → parallel tools × 4 cities → parallel mixed × 4 different tools.

The quality-bench.sh fires a domain-knowledge prompt ("What is L1 Dep in microarchitecture and how does it affect gaming performance?") against every running endpoint in parallel and lets you eyeball which model gives the sharpest answer.

HBM rises to ~90-99% used per active card. That's the vLLM pre-allocation — --gpu-memory-utilization 0.9 means the driver claims 90% of HBM upfront and manages the pool internally. It doesn't grow further. Restart the container weekly if you want to clear accumulated fragmentation (one container we restarted reclaimed 35 GiB after 5 days of varied sequence shapes).
